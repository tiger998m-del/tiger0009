# بوت تداول Binance Spot الآلي

بوت تداول آلي كامل لمنصة Binance، **Spot فقط** (بدون Futures وبدون Margin وبدون
Leverage وبدون Short Selling)، يشتري عملات USDT الفورية طويلاً (Long) فقط ثم يبيعها.
المشروع مستقل بالكامل، قابل للنقل إلى أي سيرفر آخر بعد تثبيت المتطلبات وإعداد
ملف `.env`.

> **تنبيه مهم:** الوضع الافتراضي لهذا البوت هو `DRY_RUN=false`، أي **تداول حقيقي
> بأموال حقيقية على Binance فور التشغيل** بعد اجتياز فحوصات الأمان. لا تشغّل
> البوت بمفاتيح API حقيقية إلا بعد اختباره جيدًا في وضع `DRY_RUN=true` أولًا.

---

## النشر على Railway

المشروع جاهز للنشر مباشرة على [Railway](https://railway.com) كخدمة **Worker**
(عملية خلفية دائمة، وليست موقعًا يستقبل زيارات على منفذ HTTP). يحتوي المشروع
على الملفات التي يحتاجها Railway للتعرّف عليه تلقائيًا:

- `Procfile` → `worker: python main.py`
- `railway.json` → يحدد أمر التشغيل `python main.py` مع إعادة تشغيل تلقائية
  عند الفشل.
- `.python-version` → `3.11`
- `requirements.txt` → يثبَّت تلقائيًا عبر Nixpacks.

### خطوات النشر

1. ارفع مجلد المشروع إلى مستودع GitHub خاص بك (Railway يعمل بشكل أساسي عبر
   ربط مستودع Git، وليس عبر رفع ملف مضغوط مباشرة من الواجهة).
2. من لوحة Railway: **New Project → Deploy from GitHub repo** واختر المستودع.
3. بعد إنشاء الخدمة، اذهب إلى تبويب **Variables** وأضف كل المتغيرات الموجودة
   في `.env.example` بقيمها الحقيقية (`BINANCE_API_KEY`, `BINANCE_API_SECRET`,
   `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `BOT_CAPITAL_SAR`, `DRY_RUN`,
   ...إلخ). **لا ترفع ملف `.env` نفسه إلى GitHub أبدًا.**
4. تأكد أن نوع الخدمة **Worker** (لا يحتاج Domain/منفذ عام) — لا تفعّل
   "Generate Domain" لأن البوت لا يستقبل طلبات HTTP.
5. فعّل **Restart Policy: On Failure** (موجود مسبقًا في `railway.json`) حتى
   يعيد Railway تشغيل البوت تلقائيًا إن توقف لأي سبب — الاستعادة (Recovery)
   المدمجة في الكود ستتكفل باستئناف الصفقات المفتوحة بأمان.
6. راقب تبويب **Deployments → Logs** في Railway لمتابعة سجلات البوت مباشرة
   (نفس محتوى `logs/bot.log` لكن مباشرة من الخادم).
7. **تنبيه:** بيئة Railway المجانية (Free/Hobby) قد توقف الخدمة عند عدم
   النشاط أو بعد حد استهلاك الساعات الشهري. بوت تداول حقيقي بأموال فعلية
   يحتاج تشغيلًا **مستمرًا 24/7** — يُنصح باستخدام خطة مدفوعة تضمن استمرارية
   العمل، وإلا فقد تُفقَد مراقبة وقف الخسارة أثناء توقف الخدمة.

> بديل: يمكن أيضًا النشر مباشرة من جهازك دون GitHub عبر
> [Railway CLI](https://docs.railway.com/guides/cli):
> `railway login` ثم `railway init` ثم `railway up` من داخل مجلد المشروع.

## بنية المشروع

```
binance_spot_bot/
├── main.py                       # نقطة تشغيل البوت
├── requirements.txt
├── .env.example                  # انسخه إلى .env واملأه
├── .gitignore
├── pytest.ini
├── app/
│   ├── config/settings.py        # تحميل كل الإعدادات من .env فقط
│   ├── utils/                    # Logging (Rotating + إخفاء الأسرار)، تقريب Decimal، وقت UTC
│   ├── exchange/                 # Binance REST Client + Symbol Filters + الأخطاء
│   ├── symbols/                  # فلترة الكون (Market Cap / Volume / USDT Spot) + مزوّد القيمة السوقية
│   ├── marketdata/                # Kline WebSocket + Price WebSocket + مخزن الشموع المغلقة
│   ├── strategy/                  # المؤشرات + شروط الدخول الـ16 + شروط الخروج (ATR/EMA8) + محرك الإشارات
│   ├── risk/risk_manager.py       # حجم الصفقة، التوقف اليومي، الإيقاف المؤقت
│   ├── database/                  # SQLite (Trades + Risk State)
│   ├── notifications/             # Telegram
│   ├── execution/                 # تنفيذ الأوامر + إدارة الصفقات (الأقفال ومنع التكرار)
│   ├── safety/startup_checks.py   # فحص الأمان قبل التداول الحقيقي
│   └── core/                      # المنسّق الرئيسي (bot.py) + الاستعادة بعد التشغيل (recovery.py)
├── tests/                          # اختبارات الوحدة (pytest)
├── logs/                           # ملفات السجلات (Rotating)
└── data/                           # قاعدة بيانات SQLite
```

الفصل بين المكونات مطبّق حرفيًا: منطق الاستراتيجية (`strategy/`) لا يعرف شيئًا عن
Binance أو قواعد البيانات أو Telegram؛ إدارة المخاطر (`risk/`) منفصلة تمامًا عن
منطق الإشارات؛ التنفيذ (`execution/`) هو الوحيد المسموح له بإرسال أوامر حقيقية.

## 1. متطلبات Python وإنشاء البيئة الافتراضية

يتطلب المشروع **Python 3.10 أو أحدث**.

```bash
cd binance_spot_bot
python3 -m venv .venv
source .venv/bin/activate        # على Windows: .venv\Scripts\activate
```

## 2. تثبيت المتطلبات

```bash
pip install --upgrade pip
pip install -r requirements.txt
```

## 3. إنشاء ملف .env

```bash
cp .env.example .env
```

ثم افتح `.env` بأي محرر نصوص واملأ القيم. **لا يتم أبدًا** كتابة أي مفتاح أو سر
داخل الكود المصدري — كل شيء حساس يُقرأ من `.env` فقط في `app/config/settings.py`.

## 4. إضافة مفاتيح Binance API

1. سجّل الدخول إلى حسابك في Binance.
2. اذهب إلى **API Management** وأنشئ مفتاح API جديد.
3. انسخ `API Key` و `Secret Key` إلى:
   ```
   BINANCE_API_KEY=مفتاحك
   BINANCE_API_SECRET=سرّك
   ```
4. **لا تشارك** هذين المفتاحين مع أي شخص، ولا ترفعهما إلى Git أبدًا (ملف `.env`
   مُدرج في `.gitignore` مسبقًا).

## 5. إعداد صلاحيات Binance

عند إنشاء مفتاح الـ API فعّل **فقط**:

- ✅ Enable Reading
- ✅ Enable Spot & Margin Trading (Binance تسمي هذا الخيار كذلك حتى لو كنت
  ستستخدم Spot فقط؛ البوت نفسه لا يستدعي أي نقطة نهاية Margin/Futures على
  الإطلاق — راجع قسم "القرارات الهندسية" أدناه)

عطّل دائمًا:

- ❌ Enable Withdrawals (لا داعي إطلاقًا لصلاحية السحب؛ تفعيلها يشكّل خطرًا أمنيًا)
- ❌ Enable Futures
- ❌ Enable Margin Borrow/Repay/Transfer

وإن استطعت، قيّد المفتاح بعنوان IP السيرفر الذي سيشغّل البوت.

## 6. إعداد Telegram

1. تحدّث إلى [@BotFather](https://t.me/BotFather) على Telegram وأنشئ بوتًا
   جديدًا بالأمر `/newbot`، فتحصل على `TELEGRAM_BOT_TOKEN`.
2. أرسل أي رسالة إلى البوت الذي أنشأته حتى يكون بإمكانه مراسلتك.
3. احصل على `TELEGRAM_CHAT_ID` الخاص بك (رقمي) عبر مراسلة
   [@userinfobot](https://t.me/userinfobot) أو عبر استدعاء
   `https://api.telegram.org/bot<TOKEN>/getUpdates` بعد إرسال رسالة للبوت.
4. املأ في `.env`:
   ```
   TELEGRAM_BOT_TOKEN=رمز_البوت
   TELEGRAM_CHAT_ID=معرف_الدردشة_الرقمي
   TELEGRAM_USERNAME=@tiger007KSA
   ```

> `TELEGRAM_USERNAME` هو للعرض والتوثيق فقط داخل الرسائل؛ الإرسال الفعلي يعتمد
> حصريًا على `TELEGRAM_BOT_TOKEN` و `TELEGRAM_CHAT_ID`. إن تُركا فارغين، يستمر
> البوت بالعمل، لكن كل التنبيهات تُسجَّل في Logs فقط بدل الإرسال (مع تحذير واحد
> عند بدء التشغيل).

## 7. تحديد رأس المال (BOT_CAPITAL_SAR)

```
BOT_CAPITAL_SAR=1000
```

هذا هو رأس المال **المخصص لهذا البوت فقط**، وليس رصيد حسابك الكامل في Binance.
البوت لا يفترض أبدًا أن كامل رصيد الحساب متاح له — قبل كل عملية شراء يتحقق من
الرصيد الفعلي المتاح ولا يتجاوزه أبدًا (راجع `app/risk/risk_manager.py` ودالة
`compute_trade_capital`).

## 8. تحويل SAR إلى USDT

```
SAR_PER_USDT=3.75
```

هذا سعر تحويل يدوي وثابت تضبطه أنت في `.env` (القيمة الافتراضية 3.75 تقريب
لسعر صرف الريال السعودي المربوط بالدولار). راجع قسم "القرارات الهندسية" أدناه
لتفسير سبب اختيار سعر يدوي بدل الاعتماد على واجهة صرف عملات خارجية حيّة.

كل عملية حساب لرأس المال بالـ USDT تُسجَّل بوضوح في Logs عند بدء التشغيل
(`Capital=... SAR (~... USDT)`).

## 8.1 إعادة استثمار الأرباح يوميًا (REINVEST_PROFITS)

```
REINVEST_PROFITS=true   # الافتراضي: إعادة استثمار كامل الأرباح/الخسائر تلقائيًا
REINVEST_PROFITS=false  # تعطيل: التداول دائمًا بحجم رأس المال الثابت من .env فقط
```

هذه الميزة تُعرَف داخل `app/risk/risk_manager.py`. عندما تكون مفعّلة (الوضع
الافتراضي)، تُحسَب "رأس المال الفعلي" المستخدم لحجم الصفقات **مرة واحدة عند
بداية كل يوم تداول بتوقيت UTC** وفق المعادلة:

```
رأس المال الفعلي = MAX(BOT_CAPITAL_SAR/SAR_PER_USDT + إجمالي أرباح/خسائر
                         كل الصفقات المغلقة منذ بداية تشغيل البوت, 0)
```

- إجمالي الأرباح/الخسائر يُشتَق دائمًا من جدول `trades` في SQLite (وليس من
  عدّاد يُحدَّث تراكميًا)، فلا يمكن أن ينحرف عن الواقع الفعلي أبدًا، ويبقى
  صحيحًا حتى بعد إعادة تشغيل البوت.
- القيمة المحسوبة **تتجمّد ليوم تداول كامل** — إغلاق صفقة الساعة 10 صباحًا لا
  يغيّر حجم صفقة تُفتَح الساعة 11 من نفس اليوم؛ التحديث يحدث فقط عند بداية
  يوم UTC التالي (أو عند إعادة تشغيل البوت، لأن القيمة تُشتق دائمًا من الحقيقة
  الفعلية في قاعدة البيانات فإعادة التشغيل آمنة تمامًا ولا تُسبب ازدواج حساب).
- إن أدّت الخسائر المتراكمة إلى جعل رأس المال الفعلي صفرًا أو أقل، يُثبَّت عند
  صفر (Floor عند 0) — ما يعني توقف حجم الصفقة عند صفر ومنع فتح صفقات جديدة
  تلقائيًا (سلوك آمن Fail-Closed، وليس انهيارًا أو أمرًا بكمية سالبة).
- عند كل تحديث يومي، يُرسَل تنبيه Telegram بعنوان `CAPITAL SNAPSHOT` يوضّح
  رأس المال الأساسي، صافي الأرباح/الخسائر المتراكمة، رأس المال الفعلي
  المستخدم اليوم، وحجم الصفقة الواحدة (48%) الناتج — لمراقبة تراكم النمو (أو
  التراجع) بشفافية كاملة.
- نسبة **التوقف اليومي (Daily Stop = -2%)** تُحسَب أيضًا من رأس المال الفعلي
  لليوم (المُركَّب)، وليس من رأس المال الثابت — أي أن -2% اليوم هي نسبة من
  رأس المال بعد التركيب، بما يحافظ على اتساق إدارة المخاطر مع نمو/تراجع رأس
  المال الفعلي.
- تعطيل الميزة (`REINVEST_PROFITS=false`) يعيد البوت للسلوك الثابت: حجم كل
  صفقة يُحسَب دائمًا من `BOT_CAPITAL_SAR` وحده بصرف النظر عن الأرباح/الخسائر
  المتراكمة.

## 9. تحديد DRY_RUN

```
DRY_RUN=false   # تداول حقيقي بأموال حقيقية (الافتراضي)
DRY_RUN=true    # تشغيل تجريبي، لا أوامر حقيقية على الإطلاق
```

هذه القيمة مركزية: كل عمليات BUY و SELL في المشروع تمر عبر `OrderExecutor`
الذي يتحقق من هذه القيمة، فلا يمكن أبدًا أن يعمل جزء من المشروع Live وجزء آخر
Dry Run في نفس التشغيلة.

## 10. تشغيل البوت

```bash
python main.py
```

عند البدء، يطبع البوت مباشرة في الطرفية:

```
====================
LIVE TRADING MODE
REAL MONEY ENABLED
====================
```

أو في وضع التجربة:

```
====================
DRY RUN MODE
NO REAL ORDERS
====================
```

ثم يجري **فحص الأمان الكامل قبل التداول** (Startup Safety Check): الاتصال بـ
Binance، صحة المفاتيح، صلاحيات Spot، قراءة الرصيد، توفر رأس المال، معلومات
الأزواج (Exchange Info)، مزامنة الوقت مع سيرفر Binance، والوصول إلى بيانات
السوق عبر WebSocket. إن فشل أي فحص أساسي، **لا يبدأ التداول الحقيقي إطلاقًا**،
ويُسجَّل السبب في Logs وتُرسَل رسالة Telegram بذلك.

## 11. معرفة وضع التشغيل الحالي

- من الطرفية: العنوان الظاهر عند بدء التشغيل (`LIVE TRADING MODE` أو
  `DRY RUN MODE`).
- من Telegram: رسالة `BOT STARTED` تحتوي `Mode: ...` بوضوح.
- من ملف `logs/bot.log`: أول سطور التشغيل.

## 12. إيقاف البوت بطريقة سليمة

اضغط `Ctrl+C` في الطرفية (أو أرسل إشارة `SIGTERM` إن كان يعمل كخدمة). البوت
يلتقط الإشارة، يرسل تنبيه `BOT STOPPED` إلى Telegram، يوقف اتصالات WebSocket
بأمان، ويغلق قاعدة البيانات بشكل نظيف. **لا يوقف البوت الصفقات المفتوحة** —
هي تبقى محفوظة في SQLite وتُستعاد تلقائيًا عند إعادة التشغيل التالية.

## 13. إعادة التشغيل و Recovery

فقط شغّل `python main.py` مجددًا. عند كل بدء تشغيل، **قبل** البحث عن أي صفقة
جديدة، يقوم البوت بخطوات الاستعادة الكاملة (`app/core/recovery.py`):

1. قراءة الصفقات المفتوحة من SQLite.
2. قراءة أرصدة الحساب وحالة الأوامر من Binance.
3. مطابقة كل صفقة محلية مع الحقيقة الفعلية على المنصة.
4. استعادة أي صفقة متوافقة تمامًا (TP و ATR Stop ومراقبة السعر تُستأنف كما هي).
5. أي حالة غامضة أو غير متطابقة (مثلاً الكمية المحلية لا تطابق الرصيد الفعلي،
   أو أمر TP انتهى بحالة غير متوقعة) **لا يُخمَّن حلّها أبدًا** — تُوسَم الصفقة
   `NEEDS_MANUAL_REVIEW`، تُستبعد من أي إجراء آلي إضافي، ويُرسَل تنبيه Telegram
   عاجل لمراجعتها يدويًا. حماية رأس المال أهم من استمرار التشغيل الآلي.

## 14. تغيير رأس المال لاحقًا

عدّل فقط:

```
BOT_CAPITAL_SAR=5000
```

في `.env` ثم أعد تشغيل البوت. لا حاجة لأي تعديل في الكود؛ حجم كل صفقة (48%)
والحد الأقصى (96%) يُعادان حسابهما تلقائيًا من القيمة الجديدة.

## 15. التحويل بين DRY RUN و LIVE

عدّل فقط `DRY_RUN=true` أو `DRY_RUN=false` في `.env` ثم أعد التشغيل. لا حاجة
لأي تعديل كود.

## 16. قراءة Logs

- `logs/bot.log`: كل الأحداث (Startup/Shutdown، الإشارات، الأوامر، التنفيذ،
  التحديثات، الأخطاء...)، بنظام Rotating (لا يكبر الملف بلا حدود، ويُحتفَظ
  بعدد نسخ احتياطية محدود حسب `LOG_BACKUP_COUNT`).

## دستور الاستراتيجية الكامل كما نُفّذ

كل شرط ورد في المواصفات نُفِّذ حرفيًا بدون حذف أو تبسيط:

### فحص العملة قبل أي شيء (`app/symbols/universe.py`)
- زوج USDT Spot فقط، حالة `TRADING`، `isSpotTradingAllowed=true`.
- Volume 24h (بالـ USDT) ≥ `MIN_VOLUME_24H_USD` (افتراضي 50,000,000).
- Market Cap ≥ `MIN_MARKET_CAP_USD` (افتراضي 50,000,000) عبر CoinGecko.
- استبعاد العملات ذات الرافعة المدمجة (UP/DOWN/BULL/BEAR) — قرار هندسي موثّق
  أدناه.

### شروط الدخول شراء على فاصل 5 دقائق (`app/strategy/entry_signal.py`)، على
آخر شمعة **مغلقة** فقط:

| # | الشرط |
|---|-------|
| C1 | إغلاق الشمعة > EMA8 |
| C2 | إغلاق الشمعة > EMA200 |
| C3 | اختراق EMA8 لـ SMA85 من الأسفل للأعلى (تقاطع في نفس الشمعة) |
| C4 | خط MACD > خط الإشارة (Signal) |
| C5 | اختراق RSI(14) لمستوى 70 من الأسفل للأعلى |
| C6 | RSI(14) < 93 |
| C7 | MFI(14) > 50 |
| C8 | اختراق +DI(14) لمستوى 40 من الأسفل للأعلى |
| C9 | ADX(14) > 20 |
| C10 | ADX(14) < 60 |
| C11 | -DI(14) < 20 |
| C12 | الشمعة إيجابية (إغلاق > افتتاح) |
| C13 | الإغلاق > سعر الارتكاز (H+L+C)/3 لنفس الشمعة |
| C14 | الإغلاق > أعلى سعر لأعلى 5 شموع سابقة |
| C15 | حجم التداول > حجم كل واحدة من الشموع الثلاث السابقة |
| C16 | حجم التداول > 150% من متوسط حجم 20 شمعة سابقة (SMA20) |

ثم، قبل الدخول فعليًا:

- **Initial SL** يُحسَب من ATR(14) على نفس الشمعة المغلقة:
  `Initial SL = Close - ATR(14) × 1.5`.
- **Initial SL%** = `(Close − Initial SL) ÷ Close × 100`. إن تجاوز 3% تُرفَض
  الصفقة فورًا.
- **Risk/Reward = 3 ÷ Initial SL%**. إن قلّ عن 1.25 تُرفَض الصفقة.

### الخروج (`app/strategy/exit_signal.py`)، طريقتان مستقلتان، كلٌّ منهما كافٍ
بمفرده:

- **ATR Trailing Stop**: `Candidate SL = Close[-1] − ATR14[-1] × 1.5` بعد كل
  إغلاق شمعة 5 دقائق، ثم `Active SL = MAX(Previous SL, Candidate SL)` — لا
  يتراجع الوقف أبدًا. **تنفيذ** الوقف لحظي عبر Price WebSocket بمجرد وصول
  السعر إلى المستوى، دون انتظار إغلاق الشمعة (الاستثناء الوحيد لقاعدة "شموع
  مغلقة فقط").
- **كسر EMA8**: على نفس الشمعة المغلقة، الشروط الثلاثة معًا: (أ) كسر هابط
  لـ EMA8، (ب) إغلاق الشمعة أقل من أدنى سعر لأربع شموع مكتملة سابقة، (ج) حجم
  الشمعة أكبر من حجم كل من الشمعتين السابقتين.

### آلية "أمر TP وأمر SL يُلغي أحدهما الآخر"

يُطبَّق هذا في `app/execution/position_manager.py` بمنطق مُدار من البوت نفسه
بدلًا من الاعتماد على OCO الجاهز من Binance (انظر القرارات الهندسية أدناه):
عند فتح الصفقة يُوضَع أمر **LIMIT SELL** حقيقي عند سعر TP على Binance. عند
تفعيل أي من مسارَي الخروج الآخرين (ATR Stop أو كسر EMA8)، يُلغى أمر TP أولًا
(مع التحقق من أنه لم يُنفَّذ في نفس اللحظة لمنع بيع مزدوج) ثم يُنفَّذ بيع
Market. **قفل خروج الصفقة (Position Exit Lock)** يضمن أن أول سبب خروج يفوز
هو الوحيد الذي يُنفَّذ، مهما تزامنت الأسباب.

### إدارة المخاطر (`app/risk/risk_manager.py`)

- 48% من رأس المال البوت لكل صفقة، صفقتان كحد أقصى (96% استخدام أقصى، 4%
  احتياطي).
- **Daily Stop = −2%** من رأس المال، محسوبة على اليوم التقويمي بتوقيت UTC،
  تمنع فتح صفقات جديدة حتى بداية اليوم التالي (تفصيل هذا القرار أدناه).
- **Pause 60 دقيقة** بعد خسارتين متتاليتين، يمنع الدخول الجديد فقط ولا يوقف
  مراقبة أو حماية الصفقات المفتوحة إطلاقًا.
- كل حالة (PnL اليومي، عدد الخسائر المتتالية، وقت انتهاء الإيقاف) محفوظة في
  SQLite، فلا تُفقَد أو تُصفَّر بسبب إعادة تشغيل البوت.

## القرارات الهندسية الموثقة

كما طُلِب صراحة، عند الحاجة لقرار هندسي غير محسوم في المواصفات، اعتُمِد
الخيار الأكثر أمانًا لرأس المال، وهو موثّق هنا:

1. **Market Cap عبر CoinGecko**: Binance لا توفّر القيمة السوقية عبر API. تم
   استخدام واجهة CoinGecko العامة (بدون مفتاح) مع تخزين مؤقت (Cache). إذا
   تعذّر الوصول إليها أو تعذّر التأكد من القيمة السوقية لعملة معينة، **تُرفَض
   العملة تلقائيًا** (Fail Closed) بدل افتراض أنها تحقق الشرط.
2. **تحويل SAR/USDT عبر سعر يدوي ثابت (`SAR_PER_USDT`)** بدل واجهة صرف عملات
   حيّة: لتفادي الاعتماد على مصدر خارجي إضافي قد يفشل أو يعطي سعرًا غير دقيق
   في لحظة حرجة أثناء حساب رأس مال حقيقي. يمكن تحديثه يدويًا في `.env` كلما
   لزم.
3. **استبعاد Leveraged Tokens** (رموز تنتهي بـ UP/DOWN/BULL/BEAR): هذه رموز
   Spot اسميًا لدى Binance لكنها منتجات ذات رافعة داخلية، ما يخالف روح "بدون
   رافعة" حتى لو كانت مصنّفة Spot.
4. **آلية TP/SL بإدارة البوت بدل OCO الجاهز من Binance**: لأن الاستراتيجية
   تحتاج ثلاثة مسارات خروج مستقلة (TP، ATR Stop المتحرك، كسر EMA8)، بينما
   OCO يدعم مسارين ثابتين فقط، ولأن وقف ATR متحرك يتغيّر باستمرار وسيتطلب
   إعادة بناء OCO في كل تحديث. الحل المعتمد أكثر أمانًا: أمر TP حقيقي على
   المنصة (يبقى ساريًا حتى لو انقطع اتصال البوت لحظيًا)، مع منطق إلغاء متبادل
   ومراقبة مباشرة من البوت، محمي بقفل خروج ذري يمنع البيع المزدوج.
5. **حالة المخاطر (PnL اليومي/الخسائر المتتالية) عبر SQLite لا الذاكرة**: حتى
   لا يُعاد ضبط حماية "التوقف اليومي" أو "الإيقاف المؤقت" بسبب انهيار أو
   إعادة تشغيل غير مقصودة.
6. **حالة عدم اليقين تعني توقف يدوي، لا تخمين**: أي تعارض بين SQLite وواقع
   Binance عند الاستعادة، أو فشل تأكيد تنفيذ بيع أثناء الخروج، يُصنَّف
   `NEEDS_MANUAL_REVIEW` ويُخرَج من دورة التشغيل الآلي فورًا، بدل محاولة
   "الأفضل تخمينًا" التي قد تُضاعف الخطأ (بيع مزدوج أو شراء غير مقصود).
7. **مراقبة حالة الأوامر عبر REST Polling بدل User Data Stream**: أبسط
   وأكثر قابلية للتدقيق من إدارة دورة حياة `listenKey`، مع الحفاظ الكامل على
   متابعة NEW/PARTIALLY_FILLED/FILLED/CANCELED/REJECTED/EXPIRED كما يتطلب
   الدستور.
8. **عمولات غير USDT لا تُحوَّل داخل حساب PnL**: إن كانت عمولة أي تنفيذ
   بعملة غير USDT (مثل BNB)، لا تُطرَح من الربح/الخسارة المحسوبة لتفادي
   الاعتماد على سعر تحويل حيّ إضافي؛ الأثر ضئيل جدًا ومُوثَّق هنا صراحة.
9. **"اليوم" في Daily Stop = اليوم التقويمي بتوقيت UTC**: لأن Binance نفسه
   لا يملك مفهوم "يوم تداول"، واعتماد UTC هو الخيار الأكثر حيادية وقابلية
   للتكرار.
10. **إعادة استثمار الأرباح: لقطة يومية مجمّدة مشتقة من قاعدة البيانات، لا
    تركيب لحظي**: بدل إعادة حساب رأس المال بعد كل صفقة مغلقة (ما قد يجعل حجم
    الصفقة يتغيّر منتصف اليوم بطريقة يصعب تتبعها)، يُحسَب رأس المال الفعلي
    **مرة واحدة فقط عند بداية كل يوم UTC** من مجموع `pnl_usdt` لكل الصفقات
    المغلقة في SQLite (مصدر حقيقة وحيد، لا عدّاد قابل للانحراف). كما يُعاد
    اشتقاقه من الصفر عند كل إعادة تشغيل بدل الاعتماد على قيمة مخزَّنة قد تكون
    قديمة — ما يجعل إعادة التشغيل آمنة دائمًا دون احتمال ازدواج حساب. عند
    الخسارة الكاملة لرأس المال المركّب يُثبَّت عند صفر (Fail-Closed) بدل أي
    قيمة سالبة.
